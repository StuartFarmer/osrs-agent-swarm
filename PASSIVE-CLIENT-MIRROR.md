# Passive original-client mirroring: feasibility and implementation boundaries

Research date: 2026-11-17. Local RS-SDK HEAD verified as `3aa493c3d26680df5bae2b475cc1805e3db05ae3`. Research only; no running session was changed. Upstream links below use moving branches; the web tool returned cached pages dated from today to two months ago, so this is not a complete audit of the latest upstream commit.

**Conclusion:** the original TypeScript client is a credible renderer for a passive mirror, but the inspected upstream sources do not provide a ready-made attach/replay mode. This requires a new read-only transport and a consistent client bootstrap. Logging into the same account is expressly unsuitable for the requested behavior.

**Recommendation:** prove packet-driven rendering with one agent first, then solve attachment to an already-running agent. Reuse the original client bundled in our pinned RS-SDK fork, not a newly downloaded upstream client. The intended product is a selected player's original game scene, inventory, skills, and chat rendered in the spectator's browser. The agent stays headless; the spectator owns the camera and selected tab. No per-agent server-side Chromium fleet is necessary for this design, but its actual CPU, memory, bandwidth, and accelerated-tick behavior remain unmeasured.

## RS-SDK-specific findings at the pinned checkout

These are fork features, not claims about LostCityRS upstream:

- **Existing spectator feed is a different product.** [worldfeed.ts](vendor/rs-sdk/server/engine/src/web/worldfeed.ts) describes `/worldfeed` as read-only JSON world observation: entity movement, appearance, animation, overhead/public chat, zones, and roster. Its documented schema does not provide the controlled player's inventory, skill panel, interface stack, or private/game-message history. It is useful for world rendering but is not the original game client stream.
- **Packet logging is not replay.** In [Client.ts](vendor/rs-sdk/server/webclient/src/client/Client.ts), `setPacketLogging()` starts at line 738; the logger runs immediately before outbound `stream.write()` around line 4956. It keeps a bounded debug list (over 500 entries, retain 250). [LiteClient.ts](vendor/rs-sdk/server/webclient/src/lite/LiteClient.ts) explicitly treats the logging callback as a browser debug affordance. This is not an inbound session recording or a bootstrap source.
- **Same-account browser login takes control.** [World.ts](vendor/rs-sdk/server/engine/src/engine/World.ts), around lines 1015–1081, logs out/closes the old client, assigns `other.client = player.client`, changes the session UUID, sends fresh-login success, and calls `onTakeover()`. This violates passive observation even though the player object survives.
- **Existing resync helpers mutate active state.** [Player.ts](vendor/rs-sdk/server/engine/src/engine/entity/Player.ts), `onReconnect()` around line 610, clears/rebuilds the observer build area, closes modals, refreshes inventories, and adjusts movement/masks. `onTakeover()` calls it and runs a client-sync script. They are useful as a checklist of required state, not safe functions to invoke on the live agent merely to populate a mirror.
- **Headless is still a real network client.** [session.ts](vendor/rs-sdk/server/webclient/src/lite/session.ts) loads cache, connects `GameConnection`, constructs `LiteClient`, pumps incoming packets, and sends keepalives. [GameConnection.ts](vendor/rs-sdk/server/webclient/src/lite/net/GameConnection.ts) performs normal login/ISAAC setup. Consequently the agent has a full server-to-client byte stream that can be tapped without replacing its socket.
- **Own chat needs more than inbound packets.** [actions.ts](vendor/rs-sdk/server/webclient/src/lite/actions.ts), around lines 828 and 869, adds local public-chat and sent-private-message echoes because the server does not echo them to the sender. Full chat fidelity therefore also needs these local presentation events or corresponding outbound action records.
- **Local original-client bootstrap exists.** [client.ejs](vendor/rs-sdk/server/engine/view/client.ejs), around line 415, imports the browser bundle and constructs `Client`; [Client.ts](vendor/rs-sdk/server/webclient/src/client/Client.ts) has login initialization at line 4211 and `tcpIn()` at line 8445. Retaining its asset-loading/rendering path avoids rebuilding RuneScape UI in a separate dashboard.

## Engineering inference: viable passive design

The following is a proposed design inferred from the sources, not an upstream supported feature or a validated implementation.

1. **Keep the agent's only authoritative game connection.** Fan out its ordered inbound server packets to a separate authenticated observer channel. A server `NetworkPlayer.writeInner()` tap covers the inspected game-message paths, including player/NPC information; an agent-side tap in [incoming.ts](vendor/rs-sdk/server/webclient/src/lite/protocol/incoming.ts) after framing/decryption and before `dispatch()` captures actual received frames without transmitting ISAAC state, including packets the lite client deliberately ignores. Copy bytes before reusable packet buffers are overwritten. Do not consume the agent's cipher generator again to produce a second stream.
2. **Start the original client in an explicit observer mode.** Reuse cache loading and rendering, initialize its game state without calling normal account login, and feed the protocol parser from the observer stream. A canonical opcode-plus-payload representation can be reframed without ISAAC for that transport; raw encrypted packets require the correct cipher state and packet boundary. Suppress all game-action output and automatic login/reconnect paths. An observer may still need the ordinary cache/file service, which is distinct from logging a player into the world.
3. **Solve late attachment explicitly.** Either replay a complete stream recorded since session initialization, then catch up, or supply a coherent checkpoint plus subsequent packets. A bounded tail of deltas is insufficient. A checkpoint must cover map/zone and entity baseline, player identity, variables, interface/component state, inventories, stats, and retained chat as applicable. Establish a sequence boundary so live packets cannot race, duplicate, or skip the checkpoint. Observer-specific player/NPC delta tables must agree with subsequent packets.
4. **Preserve the real client while defining fidelity.** Server packets can drive its authentic panels and game state, but add the agent's local chat echoes to retain its own public/private messages. A headless client has no original browser camera, selected tab, hover state, or rendered pixels to mirror. Those can be viewer-local. Historical chat absent from a retained record cannot be recreated by attaching now. Exact visual replay additionally needs client-local actions/timing, not just server updates. The browser loop processes at most five incoming packets per iteration, so replay catch-up also needs an explicit pacing strategy rather than assuming arbitrary backlogs drain immediately.
5. **Keep observer failures isolated.** A slow/dropped observer must resynchronize or disconnect without stalling, logging out, or changing the agent. Its endpoint should reject gameplay payloads; suppressing mouse clicks alone does not block keepalives, automatic acknowledgements, or reconnect code. Scope authorization to the selected agent because the feed includes private inventory/chat state.

The smallest convincing experiment is one running headless agent, one matching original client renderer, and a receive-only packet feed with an explicit initial baseline. Verify inventory/stats/chat/scene against the agent, and verify that observer open, close, reconnect, and attempted gameplay input leave the agent's session UUID/socket and gameplay control unchanged. Late attachment during a modal interface and after map movement are necessary checks before calling it a full passive mirror.

## Which bootstrap to build

These are design options, not existing features:

| Approach | Useful for | Limitation / decision |
| --- | --- | --- |
| Record from initial client setup and replay before switching to live packets | Smallest end-to-end proof that the original renderer can consume the agent's feed | Recording size and catch-up time grow with session duration. A bounded recent tail is not sufficient. Use for a short, controlled prototype, not the long-running deployment design. |
| Snapshot the headless client's full protocol state, then apply sequenced packet updates | Preferred first investigation for on-demand viewing without changing the game server | Requires explicit mapping into the graphical client, including entity delta indexes, component mutations, appearance buffers, zones, variables, inventory, and chat. Headless deliberately omits some visual state, so completeness is not established. The SDK observation JSON is insufficient. |
| Generate a separate baseline from the engine | Fallback if the headless snapshot cannot reconstruct the required scene | Observer-specific entity/zone delta state must match subsequent packets. Cannot clear the agent's existing tracking or call its reconnect helpers. Client-only UI/chat effects still need to come from the agent. Larger engine change. |

There is already a useful building block for the snapshot option: [lite/interfaces.ts](vendor/rs-sdk/server/webclient/src/lite/interfaces.ts) keeps per-agent component mutations in `InterfaceTable`, with `owns(id)` identifying changed components against the cache baseline. This includes inventory arrays and interface text. Both clients also use shared classes such as `ClientPlayer`, `ClientNpc`, and `IfType`; see [the fork's maintenance notes](vendor/rs-sdk/server/PATCHES.md). This reduces duplication, but it is not a ready-made serialized checkpoint: class instances, typed arrays, scene state, and parser indexes still need deliberate reconstruction.

A renderer iframe provides a fresh JavaScript realm when selecting another agent. That matters because the browser client uses static `IfType.list`; the headless fork's own interface isolation comments explain the cross-player contamination risk. The existing player picker can select the observer feed, while the iframe uses the same cache and original client build. Selection must discard the previous agent's scene, components, chat and stream generation before accepting another baseline.

The fork adds protocol and behavior beyond stock LostCityRS, including its custom public-chat packet and headless client; these are documented in [PATCHES.md](vendor/rs-sdk/server/PATCHES.md). Pin the renderer and packet definitions to the running fork and identify the matching cache in the handshake. Upstream revision 289 is a starting point for understanding the code, not a guarantee that an unmodified upstream build will decode this server correctly.

## Concrete proof and acceptance criteria

No production mirror implementation is included in this research. The smallest next experiment would:

1. Capture copied `{sequence, elapsedTime, opcode, payload}` frames after `handlePacket()` reads a complete payload and before lite `dispatch()`, from one fresh test session. Include an epoch for session replacement and explicit local chat effects. Keep the ordinary agent socket, cipher, action execution, and inference wiring unchanged.
2. Add an observer entry to the pinned graphical client: load the matching cache, perform the in-game initialization normally done after login, and feed the existing packet handlers without opening an account login. Permit camera motion and local tab selection. Block gameplay interaction before local prediction and reject gameplay messages at the observer endpoint; dropping network writes alone is insufficient to prevent a misleading local screen.
3. Compare scene, inventory quantities, skill levels/XP, received chat, the agent's own speech, and an open dialogue. Check player and NPC movement through a map boundary. Record transport sequence gaps rather than silently continuing with a damaged scene.
4. Confirm that opening, closing, switching and disconnecting the viewer preserves the agent's connection/session identity, and that clicking walk, trade, items, dialogue choices or logout cannot control it. A slow observer must be dropped or resynchronized without blocking the agent loop.
5. Only after that proof, implement a consistent late-attach baseline and test attaching during activity, with an open modal and after a zone rebuild. Measure observer cost and packet backlog at ordinary and accelerated tick rates. The current browser parser's five-packets-per-loop limit makes accelerated throughput a real validation item, not just a replay concern.

For long-running use, checkpoint and stream publication need one coherent sequence boundary. Do not serialize an old snapshot and append a newer stream with an unobserved gap. A read-only feed includes the selected agent's private messages and inventory, so retain the existing roster restrictions and tunnel/authentication boundary; do not put account credentials or cipher seeds in browser URLs.

**Current 25-agent run:** no new mirror can simply subscribe to its future packets and produce a complete original client view. We have neither an installed mirror nor a complete initialization recording. A correctly implemented late-attach snapshot could support already-connected agents; the prototype's from-login recording route cannot recover their missing past. The existing world viewer and SDK inspector remain the available views.

**What this replaces:** rebuilding the native game panels in custom HTML. **What remains useful:** the world overview, player picker, and agent reasoning/tool traces. The original game client displays game state and game chat; it does not display model reasoning or historical tool calls.

Not checked: runtime rendering, a complete upstream history search, or a working checkpoint implementation. Main risk: a naive midstream tee may look plausible while silently diverging; invoking existing reconnect/takeover initialization would alter the live agent.
